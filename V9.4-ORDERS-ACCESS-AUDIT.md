# Orders access review — 2026-09-13

## Verified in repository and tests
- Connect authenticates the bearer token through Supabase Auth and loads the company from the authenticated user's profile. Caller-supplied company and Stripe account identifiers do not select a tenant.
- Orders SELECT policy in V9.0 scopes rows through `profiles.id = auth.uid()`.
- Fulfilment RPC in V9.1 restricts the target order to that user's company and accepts only fulfilment statuses.
- Refund PATCH scopes both connected account and PaymentIntent.
- Checkout price and merchant routing are read from the published offer, not caller-provided price/account identifiers.

## Fix
A signed checkout webhook previously trusted company/page metadata without comparing it to the connected account owner. A merchant-controlled Stripe checkout could therefore supply another company ID. No evidence of actual misuse was observed.

The webhook now validates immutable existing-order ownership, or checks the company's connected account and landing page ownership before a new insert. Invalid ownership is ignored without writing; lookup errors fail closed for retry. Existing orders remain associated with their original account after reconnection. Refund behavior is unchanged.

## Validation
12 Node tests pass, including cross-company checkout rejection, forged request company identifiers, invalid authentication, refund ordering, and normal checkout/refund flow. Vite build passes.

## Hosted audit supplied by owner (2026-09-13)
RLS is enabled on companies, profiles and stripe_orders. The only profiles policy is SELECT of auth.uid(); no direct profile UPDATE policy exists, so absence of a profile trigger alone is not a tenant-switch vulnerability. Orders has only the expected tenant-scoped SELECT policy, and the fulfilment function verifies the authenticated user's company.

All three tables nevertheless have excessive client grants, including TRUNCATE, REFERENCES and TRIGGER. RLS does not govern TRUNCATE or REFERENCES. This is a permission-hardening finding, not evidence that the public REST API exposes a truncation operation or that data was accessed improperly.

`supabase-v9.5-orders-least-privilege.sql` removes excess grants while retaining authenticated profile/order reads, company reads/settings updates, and tenant-scoped fulfilment RPC execution. It preserves existing RLS and server grants. The transaction checks effective privileges and rolls back on unexpected inherited or column-level access. It has been reviewed against the supplied schema but has not yet been executed on the hosted database.

Remaining: owner runs the migration; verify effective privileges, normal settings/fulfilment, and authenticated cross-tenant access. Signup and any SECURITY DEFINER membership-changing functions are outside the supplied audit and should be reviewed before live launch.

PostgreSQL reference: https://www.postgresql.org/docs/current/ddl-rowsecurity.html
